# 🛒 Olist Text-to-SQL: 비즈니스 용어 사전 RAG

한국어 질문을 SQL로 바꿔 실행하는 Text-to-SQL 챗봇입니다.
브라질 이커머스 **Olist** 데이터(주문 약 10만 건, 테이블 8개)를 대상으로 합니다.

**핵심 발견:** 최신 LLM은 SQL 문법은 이미 거의 틀리지 않지만, **"GMV", "재구매 고객"처럼 회사마다 정의가 다른 용어**에서 크게 틀립니다.
질문에 나온 용어의 정의만 골라 넣는 **용어 사전 RAG**로 실행 정확도를 **67.3% → 99.3%**로 높였습니다.

- 🔗 데모: (배포 후 링크 추가)
- 🧠 모델: Claude Haiku (Anthropic API)
- 🛠 기술: Python, SQLite, pandas, Streamlit

## 결과

50문항 평가셋, 실험마다 3회 반복 측정 (평균 ± 표준편차)

| 실험 | 전체 | 일반 질문 (30) | 용어 질문 (20) |
|---|---|---|---|
| 베이스라인: 스키마만 전달 | 67.3 ± 2.3% | 100.0 ± 0.0% | 18.3 ± 5.8% |
| 실험 1: 용어 사전 전체 전달 (1회) | 94.0% | 90.0% | 100.0% |
| **실험 2: 용어 사전 RAG** | **99.3 ± 1.2%** | **98.9 ± 1.9%** | **100.0 ± 0.0%** |

- 베이스라인에서 용어 질문 15개는 **3번 모두** 틀렸습니다. 운이 아니라 정의를 모르면 맞힐 수 없는 구조적인 약점입니다.
- 실험 1은 용어 질문을 모두 맞혔지만, **관련 없는 일반 질문에도 정의가 새어 들어가** 일반 질문 정확도가 10%p 떨어졌습니다.
- 실험 2는 질문에 나온 용어만 골라 넣어 이 부작용을 없앴습니다. 남은 오답 1개는 3번 중 2번 맞은 문제로, 질문 자체가 애매한 경우였습니다(아래 참고).

## 어떻게 진행했나

### 1. 쉬운 평가셋으로는 개선을 측정할 수 없었다
- 처음에는 유명한 연습용 DB인 **Chinook**으로 30문항을 평가했고, 베이스라인이 이미 **96.7%**였습니다.
- 더 현실적인 **Olist**로 바꾸고 함정 문제(고객 ID와 실제 고객 구분, 포르투갈어 카테고리, 여러 건으로 나뉜 결제)를 넣었지만 **93.3%**였고, 오답 2개도 월 표시 형식(`01` vs `2018-01`) 때문에 생긴 **채점 오류**였습니다.

### 2. 진짜 약점 찾기: 회사 용어
- 실제 데이터팀에서 Text-to-SQL이 틀리는 이유는 문법이 아니라 **용어 정의**라고 가정했습니다.
- 회사 용어 18개(GMV, 순매출, 객단가, 활성 판매자, 재구매 고객, 지연 배송 등)를 정의한 [`glossary.md`](glossary.md)를 만들고, 이 용어가 들어간 질문 20개를 추가했습니다.
- 각 용어 질문은 **상식적으로 해석한 답과 사전 정의대로 계산한 답이 실제로 달라지는지** 확인했습니다. 예: "불만 리뷰"를 1점만으로 보면 11,858건, 사전 정의(2점 이하)로는 15,093건.

### 3. 용어 사전 RAG
[`glossary_rag.py`](glossary_rag.py)
1. 질문에 나온 용어를 찾습니다. (예: "우수 판매자")
2. 그 정의 안에 나오는 다른 용어까지 따라갑니다. (우수 판매자 → GMV → 완료 주문)
3. 찾은 용어가 없으면 사전을 넣지 않습니다. 그래서 일반 질문은 베이스라인과 같은 프롬프트를 받습니다.

## 실패 사례와 배운 점
- **채점 기준도 틀릴 수 있다:** 정답인데 형식만 달라 오답 처리된 경우(false negative)를 직접 확인해 찾아냈고, 질문에 출력 형식을 명시해 고쳤습니다.
- **애매한 질문은 사람도 답이 갈린다:** "예상 배송일보다 늦게 도착"은 시각까지 비교할지 날짜만 비교할지 정해져 있지 않아, 모델 답이 실행마다 바뀌었습니다. 회사가 "지연 배송"을 용어 사전에 따로 정의해 두는 이유입니다.
- **모델 응답 형식:** 어려운 질문에서 응답 맨 앞에 생각 블록(ThinkingBlock)이 와서 `content[0].text`가 실패했습니다. 텍스트 블록만 골라 합치도록 고쳤습니다.

## 안전장치
- `SELECT` / `WITH`로 시작하는 쿼리만 실행
- DB를 읽기 전용으로 연결
- 20초가 넘는 쿼리는 자동 중단
- 웹 데모는 한 번 접속에 질문 20개로 제한 (API 비용 보호)

## 파일 구성

| 파일 | 역할 |
|---|---|
| `app.py` | 질문 → 프롬프트 → Claude → SQL 생성 → 실행 (터미널에서 대화형으로도 실행 가능) |
| `glossary_rag.py` | 용어 사전 검색 (의존 용어까지 따라가기) |
| `glossary.md` | 비즈니스 용어 사전 |
| `streamlit_app.py` | 웹 데모 화면 |
| `evaluate.py` | 평가셋 채점 (실행 결과 비교, 반복 측정, 변동성 분석) |
| `eval_set.json` | Olist 평가셋 50문항 (일반 30 + 용어 20), 정답 SQL은 모두 실행해 검증 |
| `eval_set_chinook.json` | Chinook 평가셋 30문항 (초기 실험) |
| `build_olist_db.py` | `data/`의 CSV 8개를 SQLite DB(`olist.db`)로 변환 |
| `results/` | 실험별 채점 결과 CSV |

## 실행 방법

```bash
python -m venv venv
venv\Scripts\activate            # Mac: source venv/bin/activate
pip install -r requirements.txt

# .env 파일에 API 키 저장
# ANTHROPIC_API_KEY=...

python build_olist_db.py         # olist.db 만들기
streamlit run streamlit_app.py   # 웹 데모
python evaluate.py --mode rag --repeat 3 --name exp2_rag   # 평가
```

`--mode`는 `none`(베이스라인), `full`(사전 전체), `rag`(용어 사전 RAG) 중 하나입니다.
